Record Pipeline Process

How one irrigation record gets from its source to every screen that shows it. One shared process, run once per load — not once per destination.

1

A source produces its own native data

Two possible sources, two different native shapes. Neither is used as-is — both get trimmed before anything else happens.

Live · CropManage
get_irrigation_detail returns APIdetail — CropManage's native fields, mostly unused.
Demo · seeded
Hardcoded demo record — already close to final shape, still gets trimmed the same way.
2

The source builds vAPIstandard — before loadDisplayRecords ever runs

Only vAPIstandard ever flows into loadDisplayRecords. Each source knows its own native field names, so each source builds this shape itself: live data's own mapper reads Id/RanchName/... off APIdetail; demo's own mapper reads eventId/ranch/... off the demo record. Both produce the identical 11-field vAPIstandard shape. This build step is separate from step 3 — it finishes before loadDisplayRecords is ever called.

3

loadDisplayRecords receives vAPIstandard, adds the bookkeeping fields

One shared function, one call per load. Takes the vAPIstandard object step 2 just built, adds id, source, lastUpdatedDate, updatedBy, the three sync-state flags — produces the single real DisplayRecords array.

4

Deployed as copies

The one DisplayRecords result gets copied out to everywhere that needs it. Each destination holds its own copy from this point on — no live link back to step 2/3.

vDOM
The grid's own copy — what actually renders.
vAPI
API's own copy, for its panel and for building the next request.
vIRR
Keeps the untouched original separately — what create_next_irrigation works from, not the deployed copy.
Timing rule: the field selection (step 2) has to see a fully-loaded source record before it runs — a half-built source record produces an incomplete DisplayRecords. In MCP mode, fetch → select → add bookkeeping needs to run as one atomic server call, so nothing downstream can act on a half-built record.
5

loadDisplayRecords runs every time, not once

Not a one-time pipeline step. Called by each process on load, after get_irrigation_detail, and anywhere else data changes — same select → sync → propagate sequence every time, so whichever token runs next always sees current data, not stale. vAPIstandard travels as a parameter (or lives briefly inside vIRR) each time this runs.

Sync direction: vDOM ↔ vIRR is bidirectional, already built. vIRR → vAPI is one-way — IRR is responsible for keeping vAPI synced, not the other way around, and vDOM never talks to vAPI directly. Every MCP token, in any process, reading from any of the three, sees the same current data after this runs.

Note — source reference: "i gave you the code from 3.4.1 that was in the que app. it is only a harness and only offline works with cors. but it works. it does the get-irr, the post, the post que, and the loaddisplay object all as one tokens work and it knows how to handle the all ranch, and ranch all plantings. all of which needs to be handled. and it has all the old code to get thru. it some point i think it does a bare script post. and it does return the correct rccHRs on a post new record."
6

Post and update change the record — then save follows

Three rules for post_new_irrigation / update_irrigation, not yet built:

1. Post success updates recordID. A new record's recordID starts at 0 (queued, not yet synced). Once CropManage accepts it and returns a real event ID, that ID has to land in the record's recordID field — flips it from queued to synced, same rule as everywhere else: recordID presence means already synced, don't post again.

2. hours (recHrs) must always be current. Any recalculation or update propagates through the same sync (step 5) so every copy — vIRR, vDOM, vAPI — shows the current value, never something stale from before the post/update.

3. Save runs automatically right after a successful post. Not a separate manual step. The moment CropManage confirms the write, the local save file captures that state too — so the next onload/restore reflects what's actually on CropManage, not a locally-queued version that's since gone stale.
